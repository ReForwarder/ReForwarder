## Per-item notes

### R-06 — Webhook delivery replay + backoff fix (Phase 3, 2026-11-05)

- **What existed:** failed deliveries + per-attempt history were persisted and viewable, but the retry sleep was `defaultRetryBaseWait * attempt` (linear) under an "exponential" comment; no re-delivery action existed, and the outbound payload was never stored on the delivery row.
- **What changed:**
  - Backoff fix (`internal/services/webhook/dispatcher.go`): `retryDelay(attempt) = min(base * 2^(attempt-1), 60s) + jitter(0, base/4)` (base 2s, cap `maxRetryWait` 60s) with an overflow guard that degrades to the cap; comment updated to match. Seams: `Dispatcher.backoffDelay` + `Dispatcher.sleep` (defaults `retryDelay`/`time.Sleep`) so tests pin the curve without waiting.
  - Payload persistence: `models.WebhookDelivery.Payload` (text, `json:"-"`, write-once at delivery time; **documented ownership deviation** — the model file was not on the owned list, but replay is meaningless without the original body and nothing else stores it; legacy rows carry an empty payload). `recordDelivery` stores the exact outbound body.
  - `Dispatcher.ReplayDelivery(webhook, delivery, body)`: single operator-initiated attempt through the SAME guarded `post()` path (static SSRF gate + guarded/proxied transport + proxy pre-flight — no bypass), appends ONE attempt row referencing the same delivery at `attempt = prior max + 1` (via `MaxAttemptNumber`), updates the delivery outcome (status/http/error — sanitized; `Attempt` deliberately untouched so the original attempt count stays the rate-limit baseline), fires the delivery callbacks.
  - Repo queries in a NEW file `internal/storage/repositories/webhook_replay_repo.go` (methods on the existing delivery/attempt repos; no existing repo file touched): `FindByID`, `UpdateReplayOutcome`, `MaxAttemptNumber`, `CountReplaysSince`.
  - Endpoint `internal/handlers/webhook_replay_handler.go` (new): `POST /workspaces/current/webhook-deliveries/{id}/replay` — requireEdit + delivery AND webhook ownership checks; only failed deliveries; 400 for legacy rows without a stored payload ("reconstruct from stored data" is impossible — the delivery row never carried the identifiers a payload needs, so refusing beats fabricating a body); rate limit max 5 replays per delivery per hour as a pure DB count (replay attempt rows are exactly the rows numbered above the delivery's `Attempt`, so the count is exact); audit event `webhook.delivery.replayed` with delivery/webhook/attempt/outcome metadata via the workspace audit logger. Route registered in `workspace_resource_routes.go` beside the deliveries list; handler wired with one struct field + one constructor line in `routes.go` (**documented ownership deviation** — mechanically required to register a new handler).
  - Frontend: `WebhookDeliveries.vue` gains a per-row Replay button (failed deliveries only, ConfirmDialog, outcome toast, list refresh) + `webhooks.ts` `replay()` + `WebhookReplayResult` type (**documented ownership deviation** — the R-06 acceptance criterion is "replay from the Logs → Outgoing Webhooks UI" and that view was not on the owned list).
- **Security notes:** replay rides the untouched SSRF stack (pinned by `TestReplayDeliveryPolicyBlockIsSanitized` — a loopback destination is blocked and the listener sees nothing); error text sanitized like live attempts; ownership double-checked on delivery AND webhook; editor-gated; audited.
- **Tests added:** `internal/services/webhook/dispatcher_replay_test.go` — curve bounds for attempts 1-5 + cap (25 samples per attempt), wide-range cap sweep incl. overflow guard, backoff seam (3 sleeps between 4 attempts, none trailing), payload stored on the delivery, replay success (attempt row #4 on the same delivery + outcome update), replay failure (failed outcome in the UPDATE vars), SSRF policy block through the replay path.
- **Results:** `go build ./...` + `go test -count=1 -race ./internal/...` green (2 pre-existing failures in the parallel R-05 WIP classification tests excluded — see limitations); gofmt clean (CRLF-stripped); `vue-tsc --noEmit` clean; vitest 9/9.
- **Limitations:** pre-payload deliveries cannot be replayed (clear 400); a replay is one attempt (retry again via the button — the per-hour cap bounds abuse); rate limit is per-delivery (not per-user); the deleted-webhook case refuses with 400 (the original endpoint target is gone).

### R-08 — Campaign A/B winner logic (Phase 3, 2026-11-05)

- **What existed:** `ABTestEnabled`/`ABTestVariants`/`ABTestWinner` existed; variants were assigned to ALL recipients (last variant absorbed the remainder) and everything was sent immediately; `ABTestWinner` was never set; no per-variant stats anywhere.
- **What changed (hold-back model for NEW campaigns + analytics-only for already-sent ones, per the roadmap's "adapt to what the code does" directive):**
  - Config fields on `models.Campaign` (AutoMigrate adds the columns — the repo's migration mechanism): `ab_test_metric` (open_rate|click_rate, default open_rate), `ab_test_window_hours` (default 24), `ab_test_min_sample` (default 50), `ab_test_winner_sent` (exactly-once guard), `ab_test_winner_stats` (the computed stats + reason persisted at decision time as the durable audit record), plus `local_send_hour` (R-09, below).
  - **Split semantics changed (documented):** variant split percentages are shares of the FULL audience and may sum to <= 100 (was == 100); the remainder is held (variant "") and receives the winner's content after the window. A 100% total (all legacy campaigns) leaves nothing held → the winner selection runs analytics-only. `assignABTestGroups` implements it (min 1 recipient per variant, preserved from the old behavior).
  - Winner selection in `campaign_processor.go` (`maybeSelectABWinner`, called at the top of every batch tick once the window since `started_at` elapses): per-variant stats from `campaign_messages` (delivered = status=sent; opens/clicks from the denormalized first-open/first-click columns — same substrate the roadmap's email_events join targets, without the dedup hazards); every variant must reach `min_sample` or the check defers (15-min rechecks bounded by a 1h grace, after which the winner is picked from best-available data so the held remainder can never strand); winner = highest configured metric rate, ties → higher open-rate, exact tie → lower variant id (variant list order); zero opens AND clicks in all variants → variant A. The decision lands through a CAS (`MarkABWinner` guards on `ab_test_winner_sent = false` — racing workers cannot double-select), the decision is logged with the full stats, and `AssignVariantToHeld` unblocks the remainder with the winning variant (the existing per-message subject override then applies the winner's subject automatically).
  - Batch loop (`HandleCampaignBatch`): held messages are skipped while the decision is pending; completion is deferred (campaign stays `sending`) until the winner is recorded — analytics-only campaigns (nothing held) hold completion until window end, then complete after the decision.
  - Repo queries in a NEW file `internal/storage/repositories/campaign_ab_repo.go`: `ABVariantStats` (FILTER aggregates, group-by variant — the held "" group is returned but never matched against variant names), `CountPendingHeld`, `AssignVariantToHeld`, `MarkABWinner` (CAS), `PendingTimezoneCounts`, `TimezoneCounts`.
  - Handler: create/update payloads accept the new config fields with validation (metric enum, window 0-8760, sample 0-1M, local_send_hour 0-23, splits <= 100) and documented defaults applied on write (`normalizeABTestConfig`); `Duplicate` copies config but not winner state. New endpoint `GET /campaigns/{id}/ab-test` (`CampaignABTestStats`: config, winner state, window end, decision record, live per-variant stats with rates + winner flags).
  - Frontend: create-modal A/B section (enable checkbox, two variant rows with subject overrides + split percentages, split/held hint, metric/window/min-sample) in `Campaigns.vue`; `CampaignDetail.vue` gains the A/B card (winner badge in the header grid + in-progress badge, per-variant table with delivered/opens/clicks/rates and a winner row tint); `campaigns.ts` + `types.ts` methods and types.
- **DB/API changes:** six additive campaign columns (AutoMigrate); `POST /campaigns` validation relaxed from split-sum==100 to <=100 (additive: legacy ==100 payloads still valid, now with zero held); `GET /campaigns/{id}/ab-test` added.
- **Security notes:** stats endpoints are workspace-scoped through `findScoped` (existing pattern); the decision is worker-side only — no client input can force a winner.
- **Tests added:** `internal/worker/campaign_winner_test.go` — selection rules (metric choice, tie-breaks, zero-engagement default, sample gate, held-group isolation), hold-back assignment (2/2 held 6 of 10; full split; tiny-audience min-1), `isHeldForWinner`, `MarkABWinner` exactly-once CAS on the fake DB, `AssignVariantToHeld` touching only pending+variant-less rows, winner check waits for the window, no-op for plain campaigns, end-to-end `campaign:start` hold-back through the fake DB (nil-producer guard), batch defers while the winner is pending, paused campaign untouched.
- **Results:** full battery green (same exclusion as R-06); gofmt clean; `vue-tsc` clean; vitest 9/9.
- **Limitations:** the winner send honors the winner variant's SUBJECT only (template variant support exists on `ABTestVariant.TemplateID` but is unused — pre-existing); `PendingTimezoneCounts`/`ABVariantStats` aggregates run once per check, measured negligible at test-group sizes; the campaign-restart watchdog re-enqueues no-op batches every 5 min for campaigns waiting on a winner/TZ window (two cheap queries per tick — noted, not fixed, `campaign_restart.go` is out of scope).

### R-09 — Timezone-aware sending (Phase 3, 2026-11-05)

- **What existed:** the stub at `campaign_processor.go:230-235` logged intent inside `SendAtLocalTime && ScheduledAt != nil` and everything went out in one batch; the subscriber `timezone` field was unused by sending.
- **What changed:**
  - Config: `SendAtLocalTime` (existing) opts in; new `local_send_hour` (0-23, nil = send immediately regardless — the documented default). Window shape: a single local hour (simplest per the roadmap).
  - Grouping + deferral in `HandleCampaignStart`: recipients are grouped by subscriber timezone (`messageTimezones` + `planTimezoneGroups`); the first batch is enqueued with `ProcessIn` delayed to the earliest window opening across groups (0 when any group is eligible now or no hour is configured). Each batch tick re-gates per message (`localSendEligibleNow`) and re-schedules at the earliest opening across the WHOLE pending pool (`PendingTimezoneCounts`, falling back to the fetched sample on query failure) — a single self-correcting batch chain instead of one task per group (documented structural choice: batch tasks process `FindPendingByCampaign` pool-wide, so per-TZ tasks without message-level eligibility would leak across groups; per-message gating gives the same per-group deferral with pause/cancel re-checked at execution).
  - Fallbacks: empty/blank timezone → server-local batch (`time.Local`); unknown IANA name → UTC (both logged); `time.LoadLocation` is cached so per-message calls are cheap.
  - DST: `nextSendWindowOpen` builds the candidate wall-clock time with `time.Date` IN the location (spring-forward gaps normalize to the next valid instant; `AddDate` advances the calendar day so deferred groups keep their local hour with the correct absolute delay) — proven across the 2026-03-29 Europe/Berlin spring-forward (30 real minutes for a 1h30 wall gap) and fall-back.
  - Pause/cancel: deferred batches re-check campaign status at execution (the existing top-of-batch guard) — pinned by test; the handler's `SkipPendingForCampaign` drains held/deferred rows on cancel.
  - Per-TZ scheduling decision is not persisted as a column: the deferral lives in the asynq delay plus the pending pool itself (the minimal approach the task allows; per-message `queued_at`/sent_at tracking covers observability).
  - Frontend: `CampaignDetail.vue` shows the timezone-aware status in the info grid and a "Subscriber Timezones" card (count badges per stored timezone value, "Server default" label for empty values, config line when local-time sending is on); create-modal local-time section in `Campaigns.vue` (checkbox + hour select with "no window" default); `GET /campaigns/{id}/timezones` (`campaign_handler.go` + route) serves the distribution.
- **Security notes:** none — scheduling only; all eligibility logic reads existing workspace-scoped data.
- **Tests added:** `internal/worker/campaign_timezone_test.go` — location fallbacks (empty/blank → server-local, unknown → UTC), window eligibility, same-day/tomorrow openings, spring-forward and fall-back DST delays, grouping dedup + per-zone eligibility at 12:00 UTC, earliest-open selection, message→timezone mapping, per-message gate only when configured.
- **Results:** full battery green (same exclusion as R-06); gofmt clean; `vue-tsc` clean; vitest 9/9.
- **Limitations:** the campaign-restart watchdog interaction noted under R-08 applies here too; a group whose hour window closes mid-batch waits for the next day's opening (documented "send at/after hour h local" semantics); recipients without a timezone follow the server clock by design (documented in the UI hint).

### R-04 — Provider event ingestion (Phase 4, 2026-11-05)

- **What existed:** only the generic bounce webhook (`/webhooks/bounce`, hard/soft by caller assertion) — no provider-native ingestion, and `EmailEventDelivered` was unreachable from any provider source (only the worker's relay-acceptance `sent` was recorded).
- **What changed:** new package `internal/services/provider_events/` with a three-layer ingestion architecture (see the package doc for the full map):
  - **Normalized event** (`events.go`): `{Provider, EventType(delivered|bounced|deferred|rejected|complained|opened|clicked), EmailUUID, Recipient, ProviderEventID, Timestamp, Classification, Diagnostic, Metadata}`. `DedupEventID` derives `sha256(provider|event_type|provider_event_id)`; events without a provider id fall back to a content hash (recipient|diagnostic) so identical replays collapse and distinct reports do not.
  - **Adapter interface** (`adapter.go`): `ProviderAdapter{Name, VerifySignature(rawBody, headers, config), ParseEvent(rawBody)}` with per-provider files: `ses.go` (SNS envelope, SignatureVersion 1 HMAC-SHA1 over the canonical field list with the configured topic secret; SignatureVersion 2 RSA/certificate deliberately refused — trust anchor stays local; SubscriptionConfirmation answered by fetching the SubscribeURL; Delivery/Bounce(Permanent→bounce:permanent, Transient→bounce:transient)/Complaint/Open/Click mapped, Send skipped), `sendgrid.go` (JSON event array; `X-SendGrid-Signature`+`X-SendGrid-Signature-Timestamp` HMAC-SHA256 with a ±10 min replay window; **documented deviation:** SendGrid's official ECDSA-signed-event scheme is NOT implemented — the verification key is provisioned beside the endpoint so the embedded-public-key design solves a problem that does not exist here; bounce carries `status` as structured smtp_code), `postmark.go` (JSON object per POST; secret via X-Postmark-Webhook / X-Postmark-Token header or Basic-auth password, constant-time; HardBounce/SoftBounce → bounce:hard/soft markers; Metadata echo carries the message UUID; SubscriptionChange skipped), `mailgun.go` (form-encoded legacy AND JSON v5 with nested signature object; HMAC-SHA256 of timestamp+token, ±15 min freshness per Mailgun's guidance; severity permanent/temporary → markers; message-headers echo and message-id both resolve the UUID; accepted/unsubscribed skipped).
  - **Ingestion service** (`service.go`): resolves the email by UUID (unresolvable → skipped and counted, never an error), classifies via R-05, records through `emailhistory.Recorder` (the existing `(email_uuid, type, provider_event_id)` unique index dedups replays; provider timestamps stored as-is — out-of-order tolerant), and applies the full permanent-bounce side-effect chain (the ingestion-side mirror of the worker's `handlePermanentRejection`: Bounce row hard, suppression upsert behind `autoSuppress`, subscriber marking via FindAllByEmail, campaign `bounced_at`, bounced timeline row) plus the complaint chain (BounceTypeComplaint + complained timeline event + subscriber complained). `ClassificationCounts` aggregates R-05 classes over the timeline.
  - **HTTP endpoint**: `POST /api/v1/webhooks/provider/{provider}` in `internal/handlers/provider_event_handler.go`, registered in `tracking_routes.go` beside the bounce webhook under `r.mw.apiKey` (same auth pattern: the provider posts with an API key in the Authorization header) with the adapter's signature verification layered on top. Raw `func(*okapi.Context)` handler — no request binding — so the signature check sees the body byte-exact; unknown provider 404, unconfigured secret 501 (`ProviderEventResponse{accepted, skipped}` on 202).
  - **Config (documented choice):** per-provider secrets from env — `POSTA_PROVIDER_SES_SECRET`, `POSTA_PROVIDER_SENDGRID_KEY`, `POSTA_PROVIDER_POSTMARK_SECRET`, `POSTA_PROVIDER_MAILGUN_KEY` in `internal/config/config.go` with empty defaults; provider ingestion is an operator-level integration (events concern mail this install relays), so one install-wide secret per provider beats per-workspace `workspace_settings` rows, and signing secrets never need per-workspace storage. Empty secret ⇒ 501.
  - **`delivered` truth:** a provider `Delivery` event records `EmailEventDelivered` via `Recorder.Record` — the previously-unreachable event type — with the write-once `delivered_at` timestamp; the timeline now distinguishes relay acceptance (`sent`) from provider-confirmed delivery (`delivered`).
- **Documented deviation from the ownership list:** `internal/routes/routes.go` gained one `providerEvent` handler field + one constructor block beside the bounce webhook (the R-02 `domainSigning` precedent — mechanically required to register the endpoints).
- **Security notes:** every payload is signature-verified before parsing (401 otherwise); secrets constant-time compared (`hmac.Equal`/`subtle.ConstantTimeCompare`); replay windows on the timestamped schemes; the raw payload is captured into `incoming_webhook_events` only after verification (nothing unverifiable is persisted); bodies capped at 2 MiB.
- **Tests added:** `internal/services/provider_events/provider_events_test.go` — adapter fixtures per provider (SES SNS wrapper + bounce/delivery/complaint/send + SubscriptionConfirmation with a stubbed fetch; SendGrid array incl. blocked/dropped/deferred/open/click/spamreport/processed-skip; Postmark Delivery/Bounce(Hard+Soft)/SpamComplaint/Open/Click/SubscriptionChange-skip; Mailgun form + JSON signature object + temporary failure + non-delivery skip), signature matrices (valid/tampered/wrong-secret/stale/missing) with the canonical strings computed by hand in the tests, dedup-id stability, and the ingestion service on a DryRun gorm capture (delivered truth + timestamp update, permanent-bounce chain incl. suppression on/off, soft-bounce no-suppression, complaint chain, deferred, unknown-UUID skip + raw capture annotation, malformed batches, analytics query shape). `internal/handlers/provider_event_handler_test.go` — real okapi stack: 404 unknown provider, 501 unconfigured, 401 bad signature, 202 with `{accepted, skipped}` shape, raw passthrough, 400 on malformed body.
- **Results:** `go build ./...` + `go test -count=1 -race ./internal/...` green; gofmt clean (CRLF-stripped). Backend-only; frontend n/a.
- **Limitations:** resolution relies on echoed identity — stamped `X-Posta-ID` header (SES `mail.headers` when the config set includes headers, Mailgun `message-headers`), echoed metadata (Postmark), custom args or the truncated Message-ID (SendGrid); events without any echo are skipped and searchable in `incoming_webhook_events`. SES SignatureVersion 2 and SendGrid ECDSA are documented non-goals. The endpoints answer 501 until an operator sets the env secrets; no UI for provider config (backend scope).

### R-05 — Bounce/failure classification (Phase 4, 2026-11-05)

- **What existed:** a binary decision — `permanentRejection` (5xx at RCPT TO) → hard bounce + auto-suppress; everything else → retry with no recorded cause.
- **What changed:**
  - **Classifier** `internal/services/provider_events/classifier.go`: `Classification` string enum (`hard_bounce, soft_bounce, mailbox_full, invalid_recipient, dns_failure, connection_failure, tls_failure, reputation, rate_limited, deferred, auth_failure, complaint, delivered, unknown`) with `Classify(provider, eventType, smtpCode, enhancedCode, diagnostic)`. Authority order: adapter permanence markers (`bounce:permanent|hard|transient|soft` — the provider's own verdict) > RFC 3463 enhanced status code (`5.1.1/5.1.6/…→ invalid_recipient`, `x.2.2 → mailbox_full`, `5.1.2 → dns_failure`, `x.4.1/4.2 → connection_failure`, `x.4.3/4.4 → dns_failure`, `5.7.9–5.7.14 → auth_failure`, `5.7.1/5.7.26 → reputation`, `4.7.x → reputation`) > diagnostic-text patterns for the common cases (gmail "rate limit", Outlook "greylisted", quota errors, blacklists, TLS/DNS/connection failures) > reply-code class (5xx → hard_bounce, 4xx → deferred). Codes embedded in the diagnostic text are extracted when no structured code exists. Bounced-with-no-signal defaults soft (wrongly suppressing a deliverable address is worse than retrying a dead one); deferred events demote permanent-looking results. `Permanent()` = exactly {hard_bounce, invalid_recipient} — the single suppress/retry switch. `ClassifySendError(*email.SendError)` adapts the worker path (falls back to the wrapped error text when Msg is empty).
  - **Worker integration** (`internal/worker/handler.go`): the error path now classifies before deciding — permanent classes keep the existing auto-suppress; soft/deferred classes (reputation blocks, auth failures, quota, transient policy rejections) increment RetryCount without suppression through the existing retry path, with the classification + smtp_code + stage on the failed timeline event. `handlePermanentRejection(em, se, cls)` writes the classification onto the Bounce record's `Reason` (`"<class>: <reason>"`) and into both timeline events' metadata (`classification`, plus smtp_code/stage/recipient).
  - **Ingestion integration:** provider events carry the classification in the email_event Metadata (see R-04); permanent classes trigger the same suppression chain.
  - **Analytics (documented choice):** classification counts live in the email_events `Metadata` JSONB (`metadata->>'classification'`) — no schema migration, the timeline row already carries everything, and a dedicated column can be added later without losing data; `IngestionService.ClassificationCounts` groups over it with an optional occurred_at range.
- **Security notes:** none — classification only; no new inputs beyond the (verified) webhook payloads covered by R-04.

### R-22 — SMTP client timeouts/deadlines (Phase 2, 2026-11-05)

- **What existed:** all six dial sites in `internal/services/email/smtp_sender.go` used bare `tls.Dial`/`smtp.Dial` with no timeout and no deadline; a relay that accepted the connection and never replied wedged a worker concurrency slot forever.
- **What changed:** `dialSMTP(addr, host, encryption, tlsConfig)` is the single connection path for both `Send` and `TestConnection` — `net.Dialer{Timeout}` for plain/STARTTLS, `tls.DialWithDialer` for implicit TLS (handshake included), then `conn.SetDeadline(now + 4*dialTimeout)` as the overall session budget (documented simplification: a flat budget, not per-command accounting; the DATA phase gets a fresh budget of the same size because it is the only long operation). The three per-encryption send helpers collapsed into `dialSMTP` + `sendViaClient(client, conn, ...)`. `POSTA_SMTP_DIAL_TIMEOUT_SECS` (default 15) added to `internal/config/config.go`, wired via `email.SetDialTimeout(...)` once in `cmd/posta/server.go` + `worker.go` (package-level setting because senders are constructed in ~6 places; zero/negative values keep the default so a typo cannot disable the bound). `SendError.TimedOut()` classifies `net.Error` timeouts; timeouts carry Code 0 so `Permanent()` is false and the worker's `permanentRejection` predicate (Permanent && Stage=="RCPT TO") can never match them — proven by test.
- **Security notes:** none — network-level change only; credential/auth/TLS behavior untouched (STARTTLS and implicit-TLS paths covered by tests).
- **Tests added:** `internal/services/email/smtp_sender_timeout_test.go` — dial-timeout default/setter contract; `TestSendErrorTimeoutIsTransient` (timeout SendError is TimedOut, not Permanent, and fails the exact worker predicate while a 550 RCPT TO satisfies it); black-holed relay (accepts, never replies) fails within the overall budget for plain AND implicit TLS; mid-conversation stall fails within the budget; a working in-process relay still completes a full session (guards the `smtp.Dial` -> dialer+`NewClient` refactor).
- **Results:** `go build ./...` + `go test -count=1 -race ./internal/...` green; gofmt clean.
- **Limitations:** the overall budget scales with the dial timeout only — a 25 MB message on a very slow link needs `POSTA_SMTP_DIAL_TIMEOUT_SECS` raised; per-command deadlines (the reference platform-style) are the future refinement. asynq task `Timeout` was deliberately not set — the connection deadline bounds the send; a task-level timeout would duplicate the same bound.

### R-02 — DKIM signing + key lifecycle (Phase 2, 2026-11-05)

- **What existed:** DKIM was verified as DNS *presence* only (`posta._domainkey` CNAME check in the domain verifier); every workspace without an upstream signer shipped unsigned mail.
- **What changed:**
  - Dependency: `github.com/emersion/go-msgauth v0.7.0` (DKIM1, RSA-SHA256 + Ed25519-SHA256, `dkim.Sign`/`dkim.VerifyWithOptions`).
  - Model `internal/models/domain_signing_key.go` + repo `internal/storage/repositories/domain_signing_key_repo.go` + AutoMigrate registration and FK `fk_domain_signing_keys_domain` (CASCADE) in `internal/storage/migration/`. **Documented lifecycle decision:** `status` (active -> retiring -> retired, deletable when retired) models rotation; `dns_state` (pending-retry -> published) is the separate DNS-publication tracker — two fields, not one enum, because rotation and DNS confirmation are independent axes (the roadmap's corrected the reference platform semantics: no Pending stage between Active and Retiring). Rotation is API-driven with the retiring key kept until manually retired — the documented simplification vs the reference platform's scheduled rotation task.
  - Service `internal/services/email/dkim_signer.go`: `DkimSigningService.SignForDomain(msg, domain)` — resolver finds the newest Active+published key for the domain (join on domains, case-insensitive); no key -> message unchanged (unsigned is the valid CNAME/upstream-signer mode; the service also re-checks `CanSign()` as defense in depth); lookup/parse/signing **error -> fail the send** with a wrapped error that asynq retries (documented policy: silently dropping a configured signature is worse than a retried failure). RSA-2048/Ed25519 keygen, PKCS1(+PKCS8-tolerant) parsing, encrypted storage via `internal/services/crypto` (AES-256-GCM `enc:` format), DNS TXT builder (`v=DKIM1; h=sha256; k=rsa|ed25519; p=...` — Ed25519 `p=` is the raw 32-octet key per RFC 8463, which is what go-msgauth's verifier decodes), selector validation (labels may not start/end with a hyphen, 63-char labels), and `VerifyDNSPublication` via `net.LookupTXT` (test seam `email.TestLookupTXT`).
  - Signing hook: `SMTPSender` gains the optional `DkimSigner` interface field (`SetDkimSigner`, nil = unsigned/CNAME mode) checked in `Send` between `buildMessage` and the SMTP conversation, with a process-wide fallback (`email.SetDkimSigner`) wired once in `cmd/posta/server.go` + `worker.go` next to `SetDialTimeout` — every delivery path (HTTP sync fallback, relay, worker, retry worker, notifications) signs without touching each construction site. A signing failure returns a `DKIM signing failed` error, which is transient-retryable and can never trigger auto-suppression.
  - Endpoints (`internal/handlers/domain_signing_handler.go`, workspace-scoped, `requireEdit`, ownership resolved through the domain — foreign domain -> 404): POST `/domains/{id}/signing-keys` {selector, algorithm} (409 while an active key exists — use rotate), GET `/domains/{id}/signing-keys`, POST `/domains/{id}/signing-keys/rotate` (atomic demote+insert transaction; replacement selector must differ), POST `/domains/{id}/signing-keys/{keyId}/verify-dns` (records published+timestamp or pending-retry), DELETE `/domains/{id}/signing-keys/{keyId}` (retired only). **The private key never leaves the server:** generated in-process, stored encrypted, `PrivateKeyPem` carries no JSON tag, and responses expose only the `SigningKeyView` shape (id/selector/algorithm/status/dns_state/dns_record). Audit events for create/rotate/dns_published/delete. Routes registered in `workspace_resource_routes.go` (literal `rotate` before `{keyId:int}`); the handler lives on the router as `domainSigning` (one field + one constructor line in `routes.go` — documented deviation, mechanically required to register new endpoints).
  - Frontend: `Domains.vue` DNS panel gains a "DKIM signing" section — generate/rotate form (selector + algorithm; rotate needs confirmation), key cards with status/dns badges, the TXT record with copy buttons, Check-DNS and Delete actions; `web/src/api/domains.ts` + types.
- **Security notes:** private keys are AES-256-GCM encrypted at rest (`crypto.Encrypt`; base64 fallback mirrors SMTP-password behavior when `POSTA_ENCRYPTION_KEY` is unset) and never serialized; all endpoints are scope-checked (`ownsResource` on the domain) and editor-gated; custom headers were already blocked from overriding `DKIM-*` (`filterCustomHeaders`), and the signer prepends its own DKIM-Signature so a smuggled one cannot collide.
- **Tests added:** `internal/services/email/dkim_signer_test.go` — golden-message tests with fixed embedded test keys (RSA + Ed25519): sign the fixed message, then verify **through the library's own `dkim.VerifyWithOptions`** with a stubbed TXT lookup fed by `DnsTXTRecord` — signature verifies, tampered body fails, identity d= matches; unsigned passthrough; unpublished key does not sign; resolver error and unusable stored key fail; DNS-record shapes (RSA PKCS#1 `p=`, Ed25519 raw 32-byte `p=`); keygen round-trip; selector validation; `VerifyDNSPublication` (found/k-mismatch/NXDOMAIN/no-p=). - **Results:** full battery green; gofmt clean; `vue-tsc --noEmit` clean; vitest 9/9.
- **Limitations:** rotation is manual end-to-end (publish new record -> verify -> retire -> delete); the fixed `posta._domainkey` CNAME check in the domain verifier is untouched (per scope), so the DKIMVerified DNS flag still reflects the CNAME path only — the managed key's own record is checked through verify-dns; DMARC alignment holds because d= is always the From-domain; `FindActiveByDomain` runs an indexed join per send, measured negligible at current volume.
