## Per-item notes

### R-27 — Bound the retry sweep query (Phase 5, 2026-11-06)

- **What existed:** `FindFailedForRetry(ByWorkspace)` had no LIMIT (`email_repo.go`); every sweep tick loaded ALL failed emails per server and re-enqueued them — one bad hour became a requeue storm.
- **What changed:** both repo queries gained a `limit` parameter (<= 0 = unbounded escape hatch, documented); the retry worker (`internal/services/retry/worker.go`) passes `DefaultBatchLimit` (200) per server per tick — oldest first, and each claimed row leaves the failed set, so the backlog drains in bounded batches across ticks. The sweep is also jitter-spread: the loop delays up to 10% of the interval (seam `SetJitter`, sampled via `Jitter()`) before processing, so processes started together do not stampede. `processRetries` was exported as `ProcessRetries` so a single sweep can be driven from the test package.
- **Tests added:** `internal/worker/retry_bound_test.go` (NEW; fake database/sql driver self-contained to this file): bounded batch drains 5-row backlog in 2-2-1 batches oldest-first, drained backlog re-sweeps nothing, retry_count incremented once per claim, unbounded (limit 0) loads everything (legacy path pinned), exhausted-retry rows skipped, the jittered loop sweeps and stops cleanly, default jitter stays within [0, interval/10).
- **Results:** full battery green; gofmt clean.
- **Limitations:** 50k-row backlogs drain at DefaultBatchLimit per interval per server (tunable via `SetBatchLimit`; not config-exposed — operators adjust code-level constants, matching the rest of the worker).

### R-28 — Scope `?token=` API-key auth to SSE routes (Phase 5, 2026-11-06)

- **What existed:** `Authenticate` read `?token=psk_…` on EVERY authenticated route (`middleware.go:180`); the frontend never uses it (all SSE is cookie-authenticated), so URL-borne credentials could land in proxy/access logs.
- **What changed:** the query param is honored only when the request path's last segment is `stream` or ends `-stream` (`queryTokenAllowed`) — the actual SSE endpoints (`/message-stream`, `/inbound-stream`, `/admin/{events,metrics,security/events}/stream`). Plain JSON routes must present the key in the Authorization header (unchanged); a `?token=` there now falls through to JWT handling and 401s. The JWT query-token exclusion is untouched.
- **Tests added:** `internal/middlewares/rate_limit_test.go` (NEW; shared with R-15/R-18): `queryTokenAllowed` path table, `?token=psk` on a plain route 401s without reaching the API-key path, the same credential dispatches to the API-key path on `/message-stream`, header credentials still dispatch on plain routes. `authenticate_test.go`'s dispatch table updated for the R-28 semantics — the old "query on plain route reaches the API-key path" case now pins the query dispatch on an SSE path instead (mechanically required by the changed behavior; the case's purpose — query dispatch reaches the key path — is preserved).
- **Results:** full battery green; gofmt clean.
- **Limitations:** machine clients that relied on `?token=` on non-SSE routes must switch to the Authorization header (breaking, intentional — that is the acceptance criterion). `queryTokenAllowed` is a last-segment suffix rule (`stream` / `-stream` — gate at `internal/middlewares/middleware.go:243`, definition at `:278`), not a constant-path allowlist: equivalent on today's route set (the only five matching registered paths are the SSE streams), but a future non-SSE route ending in `-stream` would silently accept query-token API keys (recorded per the 2026-11-07 audit).

### R-15 — Per-API-key rate limits (Phase 5, 2026-11-06)

- **What existed:** keys carried scopes + IP allowlists but no rate limits; `AllowWithLimits(ctx, subject, hourly, daily)` (0 = unlimited) existed unused in `redis_limiter.go` and is reused as-is.
- **What changed:** `models.APIKey` gains `rate_limit_hourly` / `rate_limit_daily` (0 = unlimited; AutoMigrate adds the columns). `authenticateAPIKey` checks the key's own caps at the verified seam (after the IP allowlist, before any handler) through a new `apiKeyRateLimitCheck` seam: a exceeded cap answers 429 `API key rate limit exceeded`, a limiter infrastructure error fails OPEN (same choice as `AllowLogin` — a Redis outage degrades enforcement instead of locking out limited keys), and keys without limits cost zero Redis traffic. The Redis subject is `apikey:<id>`, so per-key counters cannot cross. ### R-13 — Scheduled (cron) automation triggers (Phase 5, 2026-11-06)

- **What existed:** automations were purely event-triggered; the engine loop (`Engine.loop`, 10s tick) already ran in-process with a persisted-stats mechanism (`Automation.Stats` JSONB) and `robfig/cron/v3` was already a dependency.
- **What changed:**
  - Trigger kind `schedule` (`models.AutomationEventSchedule`) with `AutomationTriggerConfig.CronExpression` (standard 5-field, `CRON_TZ=` honored by `cron.ParseStandard`) and `SegmentID` — the audience is the trigger's list (`ListID`, falling back to the automation-level list) or a saved segment (segment wins when both are set). Validation (domain.go): a schedule trigger requires a parsable cron expression and an audience. Empty frequency defaults to `every_time` for schedule triggers (a recurring digest silenced by the once-forever dedup would be surprising); explicit `once` keeps the per-contact trigger-log dedup.
  - Scheduler: `Engine.ProcessSchedules` runs on every loop tick. It loads live automations (GORM soft-delete-aware) whose `trigger_config` mentions "schedule" (cheap substring pre-filter, exact kind check after parse), parses the cron, and compares against the persisted checkpoint `stats.last_fired_at` (new optional `WorkflowStats` field, written by `persistScheduleCheckpoint` via `jsonb_set`). First sight checkpoints at now WITHOUT firing (creation/restarts never replay the past); the persisted checkpoint makes the check idempotent across overlapping processes. Due occurrences fire the latest one — missed intervals collapse into a single fire (digest semantics) — and the checkpoint advances. A backlog deeper than `maxScheduleCatchup` (1440 occurrences) advances the checkpoint without firing until it drains (a year-long outage with a minutely cron must not iterate half a million times).
  - `fireSchedule` resolves the audience (ownership-checked list or segment, mirroring the campaign processor's segment path) and enrolls every `subscribed` member through the normal `enrollAutomation` pipeline (conditions, frequency dedup, journey creation, nudge).
- **Frontend:** `ConfigPanel.vue` trigger "When" gains "On a schedule (cron)" — cron input with hint, list + segment audience pickers (set one), and the frequency radio (auto-defaulted to every_time when the kind is switched to schedule).
- **Documented ownership deviations:** `domain.go` (schedule validation, shared with R-14 above); none in the engine (owned files). R-12's `posta_automation_schedule_fires_total` counter fires here.
- **Tests added:** 2026-11-07 (audit follow-up — the phase originally recorded "none new" and the schedule path had zero coverage): `internal/services/automation/engine_schedule_test.go` drives the real engine `ProcessSchedules` over the fake DB/clock — TestScheduleFirstSightCheckpointsWithoutFiring (`:86`), TestScheduleFiresDueOccurrenceOnce (`:109`), TestScheduleSkipsNonLiveAutomations (`:132`), TestScheduleInvalidCronSkipped (`:148`), TestScheduleCatchupFiresNewestDueOccurrence (`:165`), TestScheduleBacklogBeyondBoundAdvancesWithoutFiring (`:184` — beyond the 1440 bound the checkpoint advances without firing), TestScheduleSegmentAudienceWins (`:206`), TestScheduleUnresolvableAudienceFiresNothing (`:243`).
- **Results:** full battery green; gofmt clean; `vue-tsc` clean.
- **Limitations:** the per-tick live-automation listing is a full scoped query every 10s (live automations are few; bounded by the substring pre-filter); one journey row + one asynq nudge per audience member per fire (matches event-trigger enrollment; very large audiences enroll in one pass — batched enrollment is a future optimization); fires are per-process safe via the checkpoint but two independent workers may both be inside `ProcessSchedules` on the same tick — the last checkpoint write wins and the overlap window is one read-modify-write (an extremely rare double-fire would still be caught by the `once` dedup for once-triggers, and is accepted for `every_time` schedules; the DB checkpoint write is the single source of truth).

### R-12 — Prometheus improvements (Phase 5, 2026-11-06)

- **What existed:** 19 metric families on the default registry; nothing exported the campaign or automation subsystems; `POSTA_METRICS_ENABLED` defaults false with the endpoint undocumented in the admin UI.

### R-05 — Bounce/failure classification (Phase 4, 2026-11-05)

- **What existed:** a binary decision — `permanentRejection` (5xx at RCPT TO) → hard bounce + auto-suppress; everything else → retry with no recorded cause.
- **What changed:**
  - **Classifier** `internal/services/provider_events/classifier.go`: `Classification` string enum (`hard_bounce, soft_bounce, mailbox_full, invalid_recipient, dns_failure, connection_failure, tls_failure, reputation, rate_limited, deferred, auth_failure, complaint, delivered, unknown`) with `Classify(provider, eventType, smtpCode, enhancedCode, diagnostic)`.
