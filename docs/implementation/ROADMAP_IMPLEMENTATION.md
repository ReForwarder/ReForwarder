## Per-item notes
### R-22 — SMTP client timeouts/deadlines (Phase 2, 2026-11-05)

- **What existed:** all six dial sites in `internal/services/email/smtp_sender.go` used bare `tls.Dial`/`smtp.Dial` with no timeout and no deadline; a relay that accepted the connection and never replied wedged a worker concurrency slot forever.
- **What changed:** `dialSMTP(addr, host, encryption, tlsConfig)` is the single connection path for both `Send` and `TestConnection` — `net.Dialer{Timeout}` for plain/STARTTLS, `tls.DialWithDialer` for implicit TLS (handshake included), then `conn.SetDeadline(now + 4*dialTimeout)` as the overall session budget (documented simplification: a flat budget, not per-command accounting; the DATA phase gets a fresh budget of the same size because it is the only long operation). The three per-encryption send helpers collapsed into `dialSMTP` + `sendViaClient(client, conn, ...)`. `POSTA_SMTP_DIAL_TIMEOUT_SECS` (default 15) added to `internal/config/config.go`, wired via `email.SetDialTimeout(...)` once in `cmd/posta/server.go` + `worker.go` (package-level setting because senders are constructed in ~6 places; zero/negative values keep the default so a typo cannot disable the bound). `SendError.TimedOut()` classifies `net.Error` timeouts; timeouts carry Code 0 so `Permanent()` is false and the worker's `permanentRejection` predicate (Permanent && Stage=="RCPT TO") can never match them — proven by test.
- **Security notes:** none — network-level change only; credential/auth/TLS behavior untouched (STARTTLS and implicit-TLS paths covered by tests).
- **Tests added:** `internal/services/email/smtp_sender_timeout_test.go` — dial-timeout default/setter contract; `TestSendErrorTimeoutIsTransient` (timeout SendError is TimedOut, not Permanent, and fails the exact worker predicate while a 550 RCPT TO satisfies it); black-holed relay (accepts, never replies) fails within the overall budget for plain AND implicit TLS; mid-conversation stall fails within the budget; a working in-process relay still completes a full session (guards the `smtp.Dial` -> dialer+`NewClient` refactor).
- **Results:** `go build ./...` + `go test -count=1 -race ./internal/...` green; gofmt clean.
- **Limitations:** the overall budget scales with the dial timeout only — a 25 MB message on a very slow link needs `POSTA_SMTP_DIAL_TIMEOUT_SECS` raised; per-command deadlines (the reference platform-style) are the future refinement. asynq task `Timeout` was deliberately not set — the connection deadline bounds the send; a task-level timeout would duplicate the same bound.

### R-03 — Delivery queue administration (Phase 2, 2026-11-05)

- **What existed:** asynq.Inspector was created in `routes.go` and used only for worker heartbeats/metrics; no cancel, no dead-letter view, no requeue, and the lost-task gap (retry worker covers only `failed`; the user retry endpoint only accepts `failed`).
- **What changed:**
  - `internal/handlers/admin_queue_handler.go` (new, methods on AdminHandler): `QueueInspector` interface (narrow slice of asynq.Inspector, adapter `AsynqQueueInspector` translates ListOptions) so the handler is testable without Redis; `GET /admin/queues` (per-queue stats + worker count, unknown queues report zeros), `GET /admin/queues/{queue}/tasks?state=pending|active|scheduled|retry|archived&page&size` (paged task lists mapped to id/type/queue/state/payload-snippet/retries/last-error/next-process), `POST .../tasks/{task_id}/cancel|run|archive` with `ErrTaskNotFound`->404, unknown-queue->404 (whitelisted to transactional/bulk/low), state conflicts->409, and audit events (`queue.task.cancelled|run|archived`) via the existing audit.Logger built from AdminHandler's event bus (no new wiring needed). Destructive routes live in `internal/routes/admin_routes.go` beside `/admin/jobs`.
  - Archive-count metric: `posta_queue_archived_tasks{queue}` GaugeVec in `internal/metrics/metrics.go`, set from the admin metrics path (`PlatformMetrics.Queues` also carries the per-queue JSON, additive field) and `ListQueues` — feeds R-12.
  - Lost-task reconcile: new `internal/cron/jobs/queue_reconcile.go` (`*/5 * * * *`, registered in `initCronManager` under `producer != nil`). Finds `status='queued' AND updated_at < now-15min` (limit 100), skips campaign-linked rows (paused campaigns release messages to queued taskless by design; the campaign-restart sweep owns those), checks the task via `GetTaskInfo(queue, "email:send:<id>")` — live states skip, archived/missing proceed — then CAS-claims (`UPDATE ... WHERE status='queued' AND updated_at < cutoff`, re-arms the window, dedupes concurrent reconcilers) and re-enqueues via the producer.
  - **Required producer change (`internal/worker/producer.go`, documented deviation from the ownership list):** `email:send` tasks now carry the deterministic TaskID `email:send:<id>` (constant shared via `internal/queues.EmailSendTaskID` — the leaf package created exactly for this, avoiding a worker<->cron/jobs import cycle). Without it `GetTaskInfo("email:send:<id>")` can never match anything (asynq auto-generates UUIDs) and the reconcile would mass-re-enqueue backlogged sends — duplicate mail. Conflict handling: `ErrTaskIDConflict` resolves via the inspector — a live task (pending/active/scheduled/retry) means dedupe success (a user-retry/retry-worker race now collapses to one task, the R-26 "TaskID dedup" foundation), while an archived dead-letter holder is deleted and the enqueue retried (asynq's ID-uniqueness check is EXISTS on the task hash key, which archived tasks hold forever).
  - Frontend: `web/src/views/admin/Jobs.vue` gains a "Delivery queues" section (per-queue stat cards with dead-letter badge, state tabs, task table with payload rendering, cancel/run/archive behind ConfirmDialog, pagination, error surface; the cron list becomes a second section); `web/src/api/admin.ts` + `web/src/api/types.ts` methods/types.
- **Security notes:** queue endpoints sit under `jwtAdminAuth` (403 for non-admin, pinned by test); cancel/run/archive are audited; unknown queues never reach Redis.
- **Tests added:** `internal/handlers/admin_queue_test.go` (stub inspector through the real okapi stack + admin JWT; events fake-driver pins the audit trail): overview stats + absent-queue zeros, paged per-state listing with payload/retry/next-process mapping, default state, invalid state 400, unknown queue 404, cancel/run/archive calls + audit events, precise 404/409 errors, non-admin 403, no-inspector 503. `internal/cron/jobs/queue_reconcile_test.go` (fake database/sql driver, the campaign_scheduler_test.go arrangement): lost task -> CAS claim + re-enqueue; pending/retry/scheduled tasks skip untouched; archived holder re-enqueues; campaign emails skipped; fresh/non-queued rows untouched; failed enqueue re-arms the window; Redis-down skips the tick; nil deps no-op.
- **Results:** full battery green (`go build ./...`, `go test -count=1 -race ./internal/...`), gofmt clean, `vue-tsc --noEmit` clean, vitest 9/9.
- **Limitations:** task-list `total` is page-local (asynq's list API is page-based; a full count would walk every page); archived tasks persist until deleted (no asynq `Retention` is configured — the dead-letter set is exactly the roadmap's assumption); the reconcile covers transactional-queue sends only, by design; one-time deploy note — emails enqueued before this change have UUID task IDs, so a genuinely-backlogged queue at deploy time may see one duplicate re-enqueue after 15 min (bounded by the CAS + batch limit).

### R-02 — DKIM signing + key lifecycle (Phase 2, 2026-11-05)

- **What existed:** DKIM was verified as DNS *presence* only (`posta._domainkey` CNAME check in the domain verifier); every workspace without an upstream signer shipped unsigned mail.
- **What changed:**
  - Dependency: `github.com/emersion/go-msgauth v0.7.0` (DKIM1, RSA-SHA256 + Ed25519-SHA256, `dkim.Sign`/`dkim.VerifyWithOptions`).
  - Model `internal/models/domain_signing_key.go` + repo `internal/storage/repositories/domain_signing_key_repo.go` + AutoMigrate registration and FK `fk_domain_signing_keys_domain` (CASCADE) in `internal/storage/migration/`. **Documented lifecycle decision:** `status` (active -> retiring -> retired, deletable when retired) models rotation; `dns_state` (pending-retry -> published) is the separate DNS-publication tracker — two fields, not one enum, because rotation and DNS confirmation are independent axes (the roadmap's corrected the reference platform semantics: no Pending stage between Active and Retiring). Rotation is API-driven with the retiring key kept until manually retired — the documented simplification vs the reference platform's scheduled rotation task.
  - Service `internal/services/email/dkim_signer.go`: `DkimSigningService.SignForDomain(msg, domain)` — resolver finds the newest Active+published key for the domain (join on domains, case-insensitive); no key -> message unchanged (unsigned is the valid CNAME/upstream-signer mode; the service also re-checks `CanSign()` as defense in depth); lookup/parse/signing **error -> fail the send** with a wrapped error that asynq retries (documented policy: silently dropping a configured signature is worse than a retried failure). RSA-2048/Ed25519 keygen, PKCS1(+PKCS8-tolerant) parsing, encrypted storage via `internal/services/crypto` (AES-256-GCM `enc:` format), DNS TXT builder (`v=DKIM1; h=sha256; k=rsa|ed25519; p=...` — Ed25519 `p=` is the raw 32-octet key per RFC 8463, which is what go-msgauth's verifier decodes), selector validation (labels may not start/end with a hyphen, 63-char labels), and `VerifyDNSPublication` via `net.LookupTXT` (test seam `email.TestLookupTXT`).
  - Signing hook: `SMTPSender` gains the optional `DkimSigner` interface field (`SetDkimSigner`, nil = unsigned/CNAME mode) checked in `Send` between `buildMessage` and the SMTP conversation, with a process-wide fallback (`email.SetDkimSigner`) wired once in `cmd/posta/server.go` + `worker.go` next to `SetDialTimeout` — every delivery path (HTTP sync fallback, relay, worker, retry worker, notifications) signs without touching each construction site. A signing failure returns a `DKIM signing failed` error, which is transient-retryable and can never trigger auto-suppression.
  - Endpoints (`internal/handlers/domain_signing_handler.go`, workspace-scoped, `requireEdit`, ownership resolved through the domain — foreign domain -> 404): POST `/domains/{id}/signing-keys` {selector, algorithm} (409 while an active key exists — use rotate), GET `/domains/{id}/signing-keys`, POST `/domains/{id}/signing-keys/rotate` (atomic demote+insert transaction; replacement selector must differ), POST `/domains/{id}/signing-keys/{keyId}/verify-dns` (records published+timestamp or pending-retry), DELETE `/domains/{id}/signing-keys/{keyId}` (retired only). **The private key never leaves the server:** generated in-process, stored encrypted, `PrivateKeyPem` carries no JSON tag, and responses expose only the `SigningKeyView` shape (id/selector/algorithm/status/dns_state/dns_record). Audit events for create/rotate/dns_published/delete. Routes registered in `workspace_resource_routes.go` (literal `rotate` before `{keyId:int}`); the handler lives on the router as `domainSigning` (one field + one constructor line in `routes.go` — documented deviation, mechanically required to register new endpoints).
  - Frontend: `Domains.vue` DNS panel gains a "DKIM signing" section — generate/rotate form (selector + algorithm; rotate needs confirmation), key cards with status/dns badges, the TXT record with copy buttons, Check-DNS and Delete actions; `web/src/api/domains.ts` + types.
- **Security notes:** private keys are AES-256-GCM encrypted at rest (`crypto.Encrypt`; base64 fallback mirrors SMTP-password behavior when `POSTA_ENCRYPTION_KEY` is unset) and never serialized; all endpoints are scope-checked (`ownsResource` on the domain) and editor-gated; custom headers were already blocked from overriding `DKIM-*` (`filterCustomHeaders`), and the signer prepends its own DKIM-Signature so a smuggled one cannot collide.
- **Tests added:** `internal/services/email/dkim_signer_test.go` — golden-message tests with fixed embedded test keys (RSA + Ed25519): sign the fixed message, then verify **through the library's own `dkim.VerifyWithOptions`** with a stubbed TXT lookup fed by `DnsTXTRecord` — signature verifies, tampered body fails, identity d= matches; unsigned passthrough; unpublished key does not sign; resolver error and unusable stored key fail; DNS-record shapes (RSA PKCS#1 `p=`, Ed25519 raw 32-byte `p=`); keygen round-trip; selector validation; `VerifyDNSPublication` (found/k-mismatch/NXDOMAIN/no-p=). The same file pins the hook: pinned signer signs on Send with the right domain, the package-level signer applies to fresh senders (the server.go/worker.go wiring), and a signing failure fails the send. `internal/handlers/domain_signing_handler_test.go` (fake-driver harness per segment_handler_test.go, domains + domain_signing_keys + events tables): generate -> 201 active/pending-retry + DNS record + **no private-key material in any response body or stored plaintext**; conflict while active exists; list shows record, no leaks; rotate -> old retiring + new active + audit event, same-selector refused; verify-dns published and pending-retry paths persist state; delete lifecycle (retiring -> 409, retired -> 204); foreign domain -> 404; selector/algorithm validation rejects without storing.
- **Results:** full battery green; gofmt clean; `vue-tsc --noEmit` clean; vitest 9/9.
- **Limitations:** rotation is manual end-to-end (publish new record -> verify -> retire -> delete); the fixed `posta._domainkey` CNAME check in the domain verifier is untouched (per scope), so the DKIMVerified DNS flag still reflects the CNAME path only — the managed key's own record is checked through verify-dns; DMARC alignment holds because d= is always the From-domain; `FindActiveByDomain` runs an indexed join per send, measured negligible at current volume.


### R-01 — Scheduled campaigns execute (Phase 1, 2026-11-05)

- **What existed:** `CampaignRepository.FindScheduledReady()` (`campaign_repo.go:152`) had zero callers. `Send` with a future `scheduled_at` atomically transitioned draft→scheduled (`campaign_handler.go:351`) and nothing ever fired it; the stuck-campaign restart cron only revived status=`sending`.
- **What changed:** new `campaign-scheduler` cron job (`internal/cron/jobs/campaign_scheduler.go`, schedule `* * * * *` — scheduled sends never wait longer than a tick) registered in `initCronManager` (`cmd/posta/server.go`) beside campaign-restart under the existing `producer != nil` guard. Each tick: `FindScheduledReady()` → atomic claim scheduled→sending via `TransitionStatus` (RowsAffected==0 → `ErrStatusConflict` → skip, another worker won) → `EnqueueCampaignStart(id)`. Enqueue failure rolls the status back to `scheduled` so the next tick retries (same rollback pattern as the Send handler). Pause/cancel during `sending` stays enforced downstream (`HandleCampaignStart` refuses non-sending rows); paused/cancelled campaigns never match the claim's `status = 'scheduled'` filter. Restart-safety is inherent: state is DB-backed (status + scheduled_at) and the every-minute poll re-finds anything left in `scheduled`; the producer TaskID `campaign:start:<id>` collapses double-fires.
- **Frontend:** Create-campaign modal (`web/src/views/campaigns/Campaigns.vue`) gained an optional "Schedule send" datetime-local field (`formScheduledAt`); sent as RFC3339 `scheduled_at` only when set — empty = send immediately. CampaignDetail's existing scheduled-time display unchanged.
- **DB/API changes:** none (existing columns and endpoint reused; no scheduler-interval setting added — the interval is the cron schedule string).
- **Security notes:** none — no new inputs; the scheduler is system-side and audience scoping happens in the worker as before.
- **Tests added:** `internal/cron/jobs/campaign_scheduler_test.go` — fake `database/sql` driver harness (the `segment_handler_test.go` pattern) driving the real `CampaignRepository`: due→claimed+enqueued; future→untouched; already-sending→untouched; paused/cancelled→untouched; claim conflict (RowsAffected 0)→no enqueue; enqueue failure→rolled back to `scheduled`.
- **Results:** `go build ./...` + `go test -count=1 -race ./internal/...` green; gofmt clean.
- **Limitations:** a hard crash in the narrow window between a successful claim and the enqueue leaves the campaign in `sending` with zero pending messages, which the campaign-restart sweep deliberately does not revive (pending==0) — the window is a single Redis call. Rows with status=`scheduled` but NULL `scheduled_at` are never picked up (Send always sets it when scheduling).
