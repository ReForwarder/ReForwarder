## 2. Core comparison table

| Security Feature | Exists in Stalwart? | Implementation Location | ReForwarder Recommendation |
|---|---|---|---|
| **Port scanning detection** | **No dedicated detector.** `BlockReason::PortScanning` is a misnomer: a fail2ban counter over **pre-auth protocol parse failures** (pooled across SMTP/IMAP/POP3/ManageSieve/HTTP, IP-keyed, 30/day → ban) plus **instant ban on HTTP banned-path globs**. No cross-port tracking, no per-IP connection rate, connect-and-abort is invisible, unbound-port probes unobservable. | `crates/common/src/network/security.rs:261-268` (`is_scanner_fail2banned`), `:270-280` (`is_http_banned_path`); trigger sites: `crates/smtp/src/inbound/session.rs:272-308`, `crates/imap/src/core/client.rs:67-94`, `crates/pop3/src/client.rs:66-87`, `crates/managesieve/src/core/client.rs:96-123`, `crates/http/src/request.rs:1036-1060`, `:846-868` | **Design fresh.** Add a per-IP connection-rate counter at accept, distinct-destination-port tracking (scoped to ports ReForwarder actually exposes), and connect-without-data counting. **Adopt** Stalwart's parse-error pooling across protocols and its banned-path glob list — both are proven, low-false-positive signals. (Report B, §5; Report F, §2–3.) |
| **Automatic IP blocking** | **Yes** — fail2ban engine: 4 fixed-window counters (auth 100/day, rcpt 35/day, scan 30/day, loiter 150/day) → `block_ip` → in-memory `RwLock<BlockedIps>` + persistent `BlockedIp` registry object + cluster broadcast. | `crates/common/src/network/security.rs:229-435`; enforcement at accept: `crates/common/src/network/listen.rs:277-285` | **Adopt.** Single-writer `BanService` (Postgres tables + in-memory snapshot + Redis pub/sub propagation) so automatic and admin writes behave identically — this also fixes Stalwart's `ReloadBlockedIps` propagation footgun. (Report C, §2; Report F, §2.) |
| **Brute-force protection** | **Yes** — dual-key fail2ban: every auth failure counts against the **source IP** *and* **blake3(login)**; either key exceeding 100/day bans the calling IP. All protocols funnel through one central `authenticate()`. Per-session caps: IMAP/POP3/Sieve 3 failures/connection, SMTP 3 errors + 5 s wait. **No account lockout** (verified absent). | `crates/common/src/network/security.rs:336-369` (`is_auth_fail2banned`), `crates/common/src/auth/authentication.rs:52-121` (funnel + 50–500 ms anti-enumeration delay); per-session: `crates/imap/src/op/authenticate.rs:228-245`, `crates/smtp/src/inbound/auth.rs:324-341` | **Adopt** the dual-key design — the single most transferable mechanism. Map onto the existing (currently unconsumed) `user.login_failed` events (`internal/handlers/user_handler.go:459-466`) → Redis counters `f2b:auth:ip:<ip>` / `f2b:auth:login:<sha256(login)>`. **Design fresh:** account lockout on N consecutive failures (Stalwart has nothing). (Report F, §2.) |
| **Connection rate limiting** | **Partial.** NO per-IP connection rate at accept (verified absent — an IP can hold the listener's full concurrency budget). What exists: global per-listener `ConcurrencyLimiter` (default 8192), per-account request rates (HTTP 1000/60 s, IMAP 2000/60 s), anonymous HTTP per-IP rate (100/60 s on ~20 public routes — **bypassed by Basic auth**, verified). | `crates/common/src/network/limiter.rs:97-126`, `crates/common/src/network/listen.rs:286-311`; rates: `crates/common/src/auth/rate_limit.rs:22-59, 61-84, 137-154`; Basic bypass: `crates/http/src/auth/authenticate.rs:71-99` | **Design fresh** the per-IP connection-rate counter at accept (Redis window at the `IPRateLimiter` seam, counting *connections*, not only requests). **Adopt** the split model: shared Redis windows for rates, in-process semaphores for concurrency. Close the Basic-auth parity gap (credential-carrying-but-unauthenticated requests still hit the anonymous limiter). |
| **Temporary bans** | **Partial.** Ban periods are configurable per reason (`authBanPeriod`, `abuseBanPeriod`, `loiterBanPeriod`, `scanBanPeriod`) and flow into `expires_at` — but **all four default to `None` → `u64::MAX` = permanent**. Out of the box, any fail2ban trip is a permanent, restart-surviving ban. | `crates/registry/src/schema/structs_impl.rs:58373-58418` (defaults), `crates/common/src/network/security.rs:217-225` (`ban_period`), `:371-380` (`block_ip`) | **Adopt** the period-per-reason mechanism; **correct the default** (finite TTLs 15 m/1 h/24 h per reason; permanent only via explicit admin action). Rationale: permanent-by-default lets an attacker hard-block a shared NAT/relay by burning 101 auth failures/day — a self-DoS for a forwarding SaaS whose inbound peers are often shared corporate relays. (Report C, §3; Report F, §2.) |
| **IPv6 blocking** | **Yes** — native v4/v6, exact /128 bans, v4-mapped-v6 canonicalized to IPv4 at accept; **no /64 (prefix) aggregation** — every key is the full 128-bit address, so native-IPv6 rotation dilutes per-IP limits. | `crates/registry/src/types/ipmask.rs:62-109, 129-173`; canonicalization: `crates/common/src/network/listen.rs:266-273`; key form: `crates/common/src/network/mod.rs:290-297` (`ip_to_bytes`) | **Adopt** (exact-IP bans via `netip.Addr`, `Unmap()` normalization). **Add** optional /64 key aggregation for rate *counters* (exact-IP bans stay default; prefix-bans as an admin action to limit collateral). |
| **CIDR blocking** | **Yes** — `IpAddrOrMask` with unique `IpMask` registry index; masks accepted `/8..=/32` (v4), `/8..=/128` (v6); `/0` catch-all not creatable via the API; `0.0.0.0` rejected. | `crates/registry/src/types/ipmask.rs:129-173` (parse), `:111-126` (index key), `:62-109` (match); index: `crates/registry/src/schema/properties_impl.rs:5544-5563` | **Adopt** (`netip.Prefix.Contains`); keep the sane mask floor (no /0 via the admin UI) and the unique-subject constraint (upsert-keeps-longer-expiry semantics). |
| **Automatic unblocking** | **Partial.** Bans expire only if a finite period was configured: expiry is a **lazy per-lookup TTL check** (expired entries skipped in memory, lingering until replaced); registry rows physically deleted **only at boot or `ReloadBlockedIps`** (with `SecurityEvent::IpBlockExpired`). **No** background sweeper, **no** cooldowns, **no** progressive escalation (counters are *reset* on ban, destroying the repeat-offender signal). | `crates/common/src/network/security.rs:441-453` (lazy check), `:510-573` (`BlockedIps::parse` purge), `:316-334` (`ban_and_reset` counter wipe); grep-verified absence of `cooldown|backoff|progressive` | **Adopt** lazy expiry (it is the right default). **Design fresh:** persisted per-IP `offense_count` in Postgres that survives ban expiry, and an escalation ladder (15 m → 1 h → 24 h → 7 d → admin review queue). |

## 5. Priority recommendation summary

- **Adopt first (P0):** accept-time IP blocklist with allowlist-wins + CIDR; dual-key (IP + login-hash) fail2ban fed by the existing `user.login_failed` events; per-request blocklist re-check for HTTP.
- **Adopt next (P1):** single-writer `BanService` with Postgres persistence + Redis pub/sub propagation (fixes the `ReloadBlockedIps` footgun); HTTP banned-path globs; **finite default ban TTLs** (correcting Stalwart's permanent-by-default); persistent offense count + escalation ladder.
- **Design fresh (Stalwart verified-absent):** dedicated port-scan signals (per-IP connection rate, distinct-port tracking, connect-abort counting), account lockout, progressive escalation, audit/history persistence, slowloris read deadlines, IPv6 /64 aggregation option.
- **Defer:** greylisting, DNSBL/spam scoring (content-level reputation matters less for a forwarding SaaS than connection-level abuse).
- **License:** Stalwart's security files are dual `AGPL-3.0-only OR LicenseRef-SEL`. The SEL side grants nothing without a paid subscription; the AGPL side is license-compatible with ReForwarder's AGPL-3.0-or-later but a Rust→Go transcription is impractical and copyleft-attracting — **clean-room design adoption is the recommendation**; cite Stalwart as design inspiration in documentation. (Report F, §1; Report E, §7.)
